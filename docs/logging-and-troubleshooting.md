# 安全技术日志与排障

技术日志用于定位程序阶段和错误，不是来源合同、原始业务资料、上传回执或价格生效证据。真实提交仍默认关闭，试点名单仍默认空；日志成功、文件回读成功和模拟核验均不能替代真实验收。

## 1. 日志来源与保存

API、worker及 `PYTHONPATH=backend .venv/bin/python -m app.capture_erp` 使用统一日志组件，在当前运行目录的 `logs/<mode>/<role>/log-<pid>-<instance>.jsonl` 保存结构化技术事件（`mode` 为demo/file/live，`role` 为api/worker/capture，后两个编号为进程号及随机实例编号）。不同模式应配置独立运行目录与数据库；日志中区分 `demo/file/live`，ERP独立只读入口始终标记 `source=erp, synthetic=false`，即使所在服务配置为demo。

`.env.example` 的日志配置：`LR_LOG_LEVEL=INFO`、`LR_LOG_MAX_BYTES=20971520`（单文件20 MiB）、`LR_LOG_RETENTION_DAYS=14`、`LR_LOG_TOTAL_BYTES=1073741824`（目录总量1 GiB）。日志清理与轮转不清理数据库、采集文件、原始Excel或回执。DEBUG只改变技术事件级别，不开启请求正文、SQL参数或凭据输出。

WSL启动脚本、Windows启动脚本和Compose API均加 `--no-access-log`，避免访问行记录路径与查询参数。Windows `runtime/api.stdout.log`、`api.stderr.log`、`worker.stdout.log`、`worker.stderr.log` 是进程输出兼容文件，不归应用轮转器管理；排障先查结构化日志，必要时在本机检查这些文件。WSL启动时进程输出仍在当前控制台。容器全部服务设置 Docker `json-file` 轮转，每文件10 MiB、保留3个文件；这是Docker标准输出轮转，与应用日志目录的保留策略不同。数据库及Web服务自身输出不等于应用安全事件。Nginx代理已使用固定安全访问格式，仅记录时间、状态码、耗时和代理自生成的 `proxy_request_id`，不记录URL、查询参数、请求头或正文；原始Nginx错误日志关闭以避免完整请求地址外泄。该代理编号不是应用 `request_id`，不能假设两者相等；代理排障仍需按时间、状态和应用错误编号关联。

独立桌面发行脚本不读取项目 `.env`，不导入 `app`，仍由用户交互输入本人密码。取数开始前在 `--output` 指定目录的 `logs/capture-<pid>-<instance>.jsonl` 配置标准库日志：每实例独立文件，单文件10 MiB、3份备份，避免并发进程共用轮转目标。只含静态事件、阶段、计数、布尔状态、随机编号和安全的文件名/函数名/行号，不含异常文案。日志目录拒绝符号链接；日志初始化或写入失败仅输出一次静态提示，不中断读取或业务证据保存，也不输出logging默认错误堆栈。`--check` 不配置日志、不创建输出目录，也不发起网络请求。桌面进度显示和业务文件不是技术日志。桌面版当前只按实例轮转，不做跨实例目录总量清理；长期多次运行后需在有权限的本机清理过期技术日志，不能顺带删除采集证据、数据库或回执。

## 2. 安全字段及ERP事件

允许记录安全的请求/任务/批次/执行/操作/采集编号、来源类型、合成标记、静态阶段、计数、耗时、HTTP状态码及受控错误码。事件文案由静态事件目录决定。禁止保存认证头、密码、令牌、Cookie、原始请求/响应、SQL参数、订单号、销售员姓名、商品价格、外部任务名、下载地址或完整异常文本。进度回调文案只用于终端展示，不能作为日志字段。

ERP接入使用以下静态事件：

- `erp.started`：一次ERP入口操作开始。
- `erp.stage`：登录、下载亏损池、提交订单导出、轮询和保存阶段，仅带静态阶段及计数。
- `erp.completed`：入口操作结束；文件中的 `capture_complete`、`selection_complete` 才是采集范围判断依据。HTTP成功和入口结束不证明来源完整。
- `erp.failed`：ERP操作失败，异常生成错误编号；批量核心保留已完成部分，不重提失败任务或自动回退逐单读取。
- `capture.saved`：文件写入及回读一致，不能解释为来源、公式或价格验收。
- `capture.failed`：采集证据保存失败。

ERP 管理员接口：`GET /api/sources/erp/sample` 和 `/validation` 只读四组第一页诊断；`GET /rates` 查询独立开放接口汇率；`POST /captures` 批量采集四类候选，可指定单类；`GET /captures/{capture_id}` 查询已保存结果。真实读取由管理员主动触发。失败时可用响应头 `X-Error-ID` 排查；批量部分失败仍保存已取得的证据，并在采集状态中说明。

## 3. 管理员日志接口

日志接口沿用管理员会话权限，销售员和主管不因此获得日志读取权限；仅查询当前运行模式的安全事件，无法指定文件路径。接口包括：

- `GET /api/logs/status`：当前进程日志写入及清理状态、配置容量、观察到的文件总量和角色更新时间，不返回真实目录。`observed_total_bytes/observed_file_count` 是本次有界扫描观测值；`usage_truncated=true` 时不能当作完整容量统计。`observed_roles` 中 `last_file_write` 仅是对应日志文件最近修改时间，不是worker心跳或存活证明；当前进程的 `last_write/write_ok` 也不能替其他进程声明健康。
- `GET /api/logs`：分页查询；`start/end` 须带时区，默认最近24小时，单次范围最多14天；`limit` 默认100、最大500，后续页使用返回的 `cursor`。
- `GET /api/logs/errors/{error_id}`：按安全错误编号定位上下文，可指定同样的时间窗口及条数上限。
- `POST /api/logs/export`：JSON请求体可带时间窗口和白名单筛选，完整扫描且符合大小限制后返回脱敏JSONL；下载前先写入管理员导出审计，审计失败不返回文件。

筛选支持角色、级别、静态事件名及 `error_id/request_id/job_id/batch_id/execution_id/capture_id/item_id/operation_id`，不支持任意正文或路径检索。查询会明确报告扫描受限，受限结果不能解释为完整检索；导出不以截断文件冒充完整导出，超过扫描或导出预算需缩小时间范围。读取对目录和文件做防符号链接检查；无法提供等价安全打开能力的平台只关闭日志读取范围，不影响独立业务流程。Windows原生Python当前缺少本实现要求的安全dirfd目录读取能力，日志查询、错误上下文和导出主动返回503，不降级成不安全读取；这属于当前明确限制，而非待验证能力。Windows仍可写入安全技术日志，并可在有权限的本机受控查看文件；网页查询可在WSL/Linux环境使用。

单次读取最多扫描32 MiB、约2秒、4096个日志文件和16384个目录条目，优先读取最近修改的文件。大文件超出剩余预算时只读尾部，并明确返回 `file_tail_truncated`；文件修改时间不代替事件时间，因此缩小时间窗口也不保证能完成全量检索。查询中的 `scanned_lines/skipped_lines/corrupt_lines/partial_lines/scanned_directory_entries` 仅统计本次实际检查部分，不推算未读取内容。达到扫描预算或发现损坏行会明确标记 `truncated`，导出拒绝不完整结果；错误编号检索未能证明检索完整时返回409，而不是把未找到解释成不存在。导出内容最大10 MiB。

## 4. 定位步骤

1. 在出错响应头或页面提示取得错误编号，记录发生时间及使用的独立运行模式；不复制完整URL、请求正文或截图中的凭据。
2. 在当前模式的应用日志目录按 `error_id` 查找错误事件，再按 `request_id`、`operation_id` 或安全任务编号查看相关阶段。同一批量操作的登录、轮询和保存共用操作编号。
3. 根据静态阶段区分来源读取、下载任务等待、证据保存或历史文件查询失败。受控错误码只是技术类别；业务文件中的部分成功、缺失订单、限流状态仍需在管理员权限下单独核对。
4. 保存错误编号、事件名、时间、阶段及应用版本供排障。提交反馈前人工确认无业务数据和凭据；原始采集文件与Excel留在受控存储，不提交Git。
5. 对已存在执行意图或结果未知的价格操作，只核验原请求，不通过重试、清库、删锁或手工重传测试结果。ERP只读取数日志不构成调价授权。

## 5. 后续开发如何增加日志

在服务或适配边界调用 `app.observability.event`，使用目录中已定义的静态事件名和字段；需要新增事件时先在 `CATALOG` 定义固定中文说明和级别，并补脱敏测试。未知事件及非白名单字段会被忽略，不应依赖任意字符串文案定位错误。纯计算层继续只返回证据，不为日志引入网络、数据库或环境配置依赖。

一次操作使用 `bind_context` 设置服务端生成的编号；捕获异常时通过 `exception=exc` 传入，只提取安全技术栈，禁止改成 `message=str(exc)`。HTTP请求上下文自动清理，持久任务的发起关联保存在 `_log_context` 保留元数据中，不能以此改变任务目标或授权。日志写入失败不应触发业务重试、释放锁或标记成功。

配置解析可能先于日志初始化失败；这时仅显示有问题的配置项名称或安全约束提示，不输出Pydantic的原始配置输入。第三方错误日志只转换为静态事件与安全栈，不直接保存其文案、SQL参数或请求地址。
