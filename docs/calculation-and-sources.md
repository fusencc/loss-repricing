# 核心计算与数据来源

本文规定 `direct-loss-v1` 的计算合同，供开发、文件对账和后续真实联调共同使用。业务依据是[已确认设计](superpowers/specs/2026-11-05-loss-repricing-design.md)，本文细化变量、单位和实现，不另创业务口径。代码位置均相对项目根目录。

**当前结论：规则及合成样本算术可在本地核对；真实数据来源、公司费用模型等价性、上传含义与平台生效尚未验收。** `direct-loss-v1` 是本项目规则版本，不是公司费率版本或上线批准。不得将 `verified=true` 这一配置值当作审核证据。

依据按层次使用：已确认设计决定本期业务规则；本文规定计算与数据合同；历史资料只提供线索；自动测试只证明给定输入下的程序行为。发生冲突时记录差异并确认，不能让旧公式、示例或测试预期替换业务决策。

### 0. 变量与金额口径

- `L`：来源的一次毛利负金额，币种为该明细的 `currency`；不是亏损率。原始金额必须保留符号。
- `q`：该金额所对应的可售件数。整单件数不能冒充某一子 SKU 的明细件数。
- `u`：正的单件亏损幅度，单位为原币/件；`Δ` 为转换后的站点币/件。
- `R`：当前含增值税（VAT）的零售价；`P`：当前实际营销售价，无营销价时为 `R`。二者均为站点币/件，不能用订单实付总额替代。
- `d`：实际价与含税零售价的比例，无量纲；`T` 为未做上传档位舍入的目标实际价；`Uraw` 为未舍入上传价；`U` 为最终含税上传价；`P'` 为折扣不变假设下的舍入后实际价。
- `a=revenue_factor`：正常收入系数，无量纲；`b=fixed_cost`：每件固定成本，站点币/件；`G(P)=a×P-b` 为每件正常一次毛利额，不是净利润或目标利润率。
- `current_margin`：来源的当前正常一次毛利率，采用比例值（例如 `-0.05` 表示 `-5%`），只用于现价不亏的排除条件。来源必须确认其费用口径、时间与模型一致，不能从显示取整的毛利率倒推成本。
- 本期费用口径排除广告与营销费用。具体包含哪些税、物流、佣金及固定费用，须以公司批准的分项公式为准；旧模板不是本期自动批准的费率表。

### 0.1 数值、空值与证据要求

核心引擎使用 `Decimal` 分子与正分母保留单件化、换汇及折扣运算的精确关系。有限小数乘加按所需位数计算，最小值和误差用交叉乘积比较，价格档位用商余数判断整档与半档，毛利按精确分子的符号判断；不使用 `float`，也不加容差把负毛利视作零。实现集中在 `domain/money.py`。

保存和展示的普通小数使用独立上下文的 **50 位有效数字**，不是 50 位小数；循环小数仍是近似显示，不能再读回这些显示值决定档位或毛利正负。新增判定另保存目标价的精确分子、分母及算术实现标识 `decimal-ratio-v1`，用于有效价容限核验。`direct-loss-v1` 的业务公式保持不变，此次修复的是数值实现偏差。

例如明细亏 1、数量 3、当前实际价 1、零售价 3，精确上传原价为 4；先把 1/3 截成有限小数再向下舍入可能错误上传 3.99。又如当前价 10、单件亏 1/3、模型 `0.9×P-9.3`，目标毛利精确为 0，不能因小数尾差误判为负。两者均有独立回归测试。

金额与费率对外优先使用十进制字符串；真实 HTTP JSON 数值直接解析为 `Decimal`，不能先过 `float`。ID 必须为文本。时间必须带时区，业务日期按北京时间。Excel 数值单元格受 15 位有效数字限制，当前模板生成器会拒绝超范围价格；文件可生成不等于真实服务认可该列。

缺失不能等于零：无营销价的空值表示已确认无折扣；未知营销价应停止该目标算价，不能传空冒充无折扣。销量 `0` 表示完整窗口内确证零销量；未知销量为 `null` 或不完整。历史 `null` 只有结合 `history_known=true` 才能表示确证无历史。`sales_complete`、`history_known` 和 `allocation_reliable` 缺失时默认 false，不能从“未提供证据”推导“已确认”；整单分摊不可靠时不参与选取，单件/明细粒度不依赖整单分摊标记。费用模型为空不设默认成本或默认系数。其他无活动/无保护等布尔值也必须有来源证据；真实 HTTP 合同要求显式映射，内部模型的默认值不构成真实数据合同。

每条判定保存规则版本、数值精度、来源引用和版本、汇率日期、模型与站点合同，以及选择明细和算价中间值。新增判定写入 `trace.formula_version`；旧历史没有此字段时按旧记录展示，不倒填为已经过新版本重算。

## 1. 本期范围与数据边界

本期只处理亏损订单对应的具体在线子SKU补亏。采用现行直接补亏公式，不采用旧15%目标利润、统一涨1%、成本20元分档、补亏再加0.5元或跨子SKU共享最小亏损。

四份候选必须齐备，包括零条记录但已确认取数完整的来源：

| 内部来源名 | 业务来源 |
|---|---|
| `loss_allocatable` | 亏损订单／可配货 |
| `loss_pending` | 亏损订单／待处理 |
| `blocked_allocatable` | 禁止发货／可配货 |
| `blocked_pending` | 禁止发货／待处理 |

这些是程序内部规范名，不代表公司API使用同名字段。`Snapshot`保存业务日期、采集时间、四来源完整标志、来源版本、原始明细引用、在线数据、汇率和站点合同。业务日按北京时间判断，当日汇率与在线观测时间不能用昨天数据顶替。

实现：`backend/app/domain/types.py`、`backend/app/domain/engine.py`、`backend/app/adapters/normalization.py`。

## 2. 每个子SKU独立取最小亏损

算价时的来源匹配身份由平台、店铺ID、站点、产品ID、具体商品ID、子SKU共同确定，ID保持文本。仓配、主SKU与费用口径还要与在线快照一致；同一身份出现冲突不会自动选一条。`VariantKey.identity()`保留源SKU，防止不同SKU的亏损混算。

防重另用`VariantKey.target_identity()`：平台、店铺ID、站点、产品ID、具体商品ID。这是实际上传对象的稳定身份，不含可变的源SKU名称或仓配；源SKU改名不能绕过未知执行锁和72小时保护。**稳定执行锁不改变算价分组，不允许把不同SKU的亏损混在一起取小。**

同一在线子SKU内，原始行ID用于跨来源去重。同一行ID出现相互冲突的金额、数量或口径会待处理；不能仅用订单号或SKU去重，因为一张订单可以有多个明细。

原始亏损记作负数`L`，数量为`q`。先得到正的单件亏损幅度`u`：

```text
已是单件金额（basis=unit）：u = abs(L)
明细金额（basis=line）：    u = abs(L) / q
整单金额（basis=order）：   只有已证实可可靠归属时，u = abs(L) / q
```

数量必须大于0；非负金额不进入亏损候选；异常记录和无法可靠分摊的整单金额不参与取小。若没有有效记录，转待处理。多SKU整单金额不能任意平均到不同SKU。

然后**仅在同一个具体在线子SKU、同店、同站、同仓配、同币种及同费用口径的有效明细内**选择最小`u`，保留被选中的原始行ID和所有参与值。两个不同子SKU即使产品ID相同，也分别计算：

| 具体子SKU | 有效单件亏损 | 选用值 |
|---|---|---:|
| A | 1、2 | 1 |
| B | 3、4 | 3 |

B不会使用A的1。这里“最小亏损”指正亏损幅度最小：原毛利`-1`与`-2`中选亏1，不是按负数数值取`-2`。主SKU维度只在销量和人工保护等已确认规则中汇总，不用于共享亏损金额。

## 3. 换汇方向

程序内部统一：`fx_rates[C]`表示**每1 CNY可兑换多少C币种单位**，且`fx_rates[CNY]=1`。例如每1 CNY对应0.6 MYR，MYR汇率为0.6。

```text
站点币补亏额 Δ = 单件原币亏损 u × 站点币每CNY汇率 / 原币每CNY汇率
```

例：CNY单件亏2，当日MYR汇率0.6，补亏额为1.2 MYR。同币种直接保留原值。内部站点币为MY→MYR、PH→PHP、SG→SGD、TH→THB、VN→VND。

原WPS模板用RMB成本除以AC汇率换成站点币，其AC在该公式中的方向与本程序相反。真实接入必须根据已确认单位转换，不可直接抄AC数值。缺币种、缺正数汇率或汇率日期错误时待处理。

## 4. 当前实际价、折扣与上传价

令`R`为当前含VAT零售价，`P`为当前实际售价：有营销价取营销价，无营销价取`R`。无折扣来源应传空值，不用零元价表示“无折扣”。必须满足`0<P<=R`。

```text
成交系数 d = P / R
无折扣： d = 1
目标实际价 T = P + Δ
未舍入的含VAT上传价 Uraw = T / d = T × R / P
```

`d`是成交比例，不是“减价百分比”。旧表里折扣55代表减55%、成交45%，不能直接当作`d=0.55`。当前引擎直接由营销价与含VAT零售价的比值求`d`。

每个站点合同必须明确适用仓配 `warehouses`、价格档位 `step`、舍入方式、税后上传列和版本，才能计算。仓配列表默认空，未明确覆盖该商品仓配时只挂起该目标；提交边界再次核对相同范围。此列表表示这些仓配已经确认可共用该上传列和费用版本，不是仅凭“直发/海外”字样猜列。需要不同列或不同模型的仓配，当前单站点合同不能同时覆盖，须分期接入或先扩展设计：

```text
档位数 n = round(Uraw / step, 合同舍入方式)
上传价 U = n × step
舍入后实际价 P' = U × d
实际价误差 ε = abs(P' - T)
```

支持的舍入方式是`ROUND_HALF_UP`、`ROUND_DOWN`、`ROUND_UP`。按档位数舍入可以支持0.025等步长，不等于固定保留两位小数。demo采用的0.01/1档位和四舍五入只是模拟合同，不能作为公司站点规则。

当前误差容限为VN≤2 VND；MY/PH/SG/TH≤0.02对应站点币。上传价非正、误差超限时待处理。真实回读误差超限还会暂停该站点新提交，旧提交继续核验。

这里存在必须保留的业务边界：按现行设计，档位舍入允许向上或向下，只要求误差在容限内及两次毛利复核通过。当前规则**没有额外要求 `P'>P` 或补亏额向上取整**，极小亏损在粗档位下可能舍入回原价。这是现有规则和测试的实际行为；若业务要求每次必有严格涨价，需要另行确认，不能擅自增加最小涨幅。

`P'=U×d` 还依赖“上传零售价后成交系数保持不变”。算术正确不证明平台会保持折扣；固定营销价、活动覆盖、税前/税后转换可能使该假设不成立。每个试点站点及仓配必须用上传前后实价证实，未证实的范围不启用真实自动提交。

## 5. 正常一次毛利复核

内部费用模型定义：

```text
normal_profit(price) = price × revenue_factor - fixed_cost
```

`price`与`fixed_cost`均为站点币，`revenue_factor`无量纲，输出为站点币毛利额。模型必须有已确认标志及版本；真实适配器要求版本与已审核站点费用模型版本一致。该模型应排除广告与营销费用。

引擎分别检查`normal_profit(T)>=0`和`normal_profit(P')>=0`。任何一个小于0则待处理。**不会把价格反解到更高盈亏平衡点，不会自动追加涨价补手续费，也不增加利润目标。** 输入的`current_margin`为当前正常一次毛利率，若已非负则本轮不调；未来来源方也必须证明该字段不含广告/营销费。

### 系数从哪里来

当前demo使用人工构造的`revenue_factor`、`fixed_cost`，只便于手工验算。`FeeModel`接收确认后的系数，代码没有凭空内置公司各站点费率。

旧WPS的U列可在未取整分子上整理成同类仿射式，但不能直接当作本期模型：

- MY/SG/VN旧收入系数为`(1-k)/(1+VAT)`；PH旧U式不除VAT；TH用每行H税率。
- 固定项由RMB成本、包材/人力/站点固定费、站点物流费及汇率组合得到，各站点公式不同。
- 旧`k=AK/100`，而`AK=SUM(AD:AJ)`包含AI列“营销费（联盟+广告）”。本期必须根据已核对的费用分解排除广告/营销，不可直接使用AK。
- 旧公式按同产品ID取最大重量，也需要核对是否适合实际子SKU和仓配。
- 一个当前毛利率观测点不能唯一确定两个未知数`revenue_factor`和`fixed_cost`。缺模型时不能默认系数1或固定成本0。

完整代数映射、原单元格与缺口见`docs/data-contract-evidence.md`第6节。真实接入应拿批准的公司费用公式/配置与独立样本核对，记录版本、单位、税基、汇率方向及生效时间；不能仅将`verified`改为true。

模型只复核目标价和舍入后实际价，不从当前毛利率拟合系数，也没有在运行时用当前毛利率重复推导公司成本。真实模型校准应在接入阶段完成：取得完整分项公式，分别在当前价和多个不同目标价计算公司预期毛利，再对照 `a×P-b`。只用一个样本或把模型标记为已确认，均不足以证明等价。

若真实费用随价格分档、有最低收费或其他非线性项，单组 `a,b` 可能不覆盖 `P`、`T`、`P'` 所在区间。当前 `FeeModel` 没有分段模型和适用价格区间字段，不能靠一个站点版本号解决该问题；须先明确适用范围，必要时经过设计确认扩展模型，再放开对应真实执行。

### 手工可验的模拟例子

某演示子SKU当前实际价10、含VAT零售价20，两笔有效单件亏损为1和2（都为站点币）；选择1。

```text
d = 10/20 = 0.5
T = 10+1 = 11
Uraw = 11/0.5 = 22
按0.01档位舍入后 U=22，P'=11，误差0
模拟毛利 = 11×0.9-9.5 = 0.4
```

这里0.9和9.5仅为演示参数，不是公司真实费用模型。

## 6. 保护、历史与执行中的关键检查

- 主SKU销量保护按同店同站前七个完整北京时间自然日汇总，不含今天；达到21件本轮不调。缺失、不完整或日期范围错误则待处理。
- 人工保护本轮不调；领取每条执行意图前检查本地最新保护名单，不等待批次缓存过期，也不为此重取整批外部数据。活动锁价、不可售等进入待处理，不自动退出活动或解除拦截。
- 已确认生效后不足72小时不再提价；恰好满72小时可以重新评估。没有有效精确生效时间时采用本程序首次成功核验时间 `confirmed_at`，不能用旧来源观测时间 `observed_at` 代替；有合法精确时间则使用 `effective_at`。证据另存时间来源，超差或未知不构成首次成功确认。已有结果未知的提交持续锁定。
- 真实有效价回读必须有匹配的站点币种，且观测年龄不超过已确认查价合同的 `max_age_seconds`。该阈值由接口证据确认，不沿用测试值或猜测统一值。未知/过期证据继续待核验。
- 核验绑定原批次的运行模式，不能用当前切换后的 demo/file/live 适配器处理其他模式历史。不同环境仍需独立数据库与运行目录，不因增加过滤就允许混用。
- 提交前重新采集和重算整批关键输入；处理超过5分钟再刷新。刷新后的价格、保护或亏损变了，就按新判定执行，不使用旧拟价。
- 单条“重新评估”只为选中的稳定上传目标保存与执行判定；采集器仍可共用完整来源快照，但不会顺带提交其他目标。该目标已有未知执行时先继续核验，不能借重评绕过锁。
- 每次提交前检查北京时间业务日；跨午夜后停止昨日未提交项，保留旧判定并排队采集新日数据。单目标重评跨日后仍保持单目标范围。已发出的请求继续独立核验。
- 执行意图和商品锁先写入数据库并提交事务，再调用外部上传。崩溃或超时不会撤回本地意图并重传，而是交给核验器。

稳定目标锁迁移保留原始Item键、判定JSON、旧锁及生效历史。同一目标若历史上已有多笔未终结执行，必须全部核验终结后才能解除其未知执行占用；一笔完成不会遗忘其余请求，较旧请求晚核验也不会把最近生效时间倒退。

全局概览/异常按批次创建时间选择每个稳定目标的最新评估，同时额外保留全部未终结执行；状态筛选发生在选取当前集合之后。旧记录的核验更新时间不会让它覆盖新评估，批次详情则保留全部历史判定和证据。

实现：`backend/app/services/execution.py`。这套流程目前通过demo回执演示，真实有效价和任务关联合同尚待接入。

## 2026-11-05 公司汇率只读接口

用户授权先接入登录与汇率查询，新增 `adapters/erp_rates.py` 和管理员 `GET /api/sources/erp/rates`，运行设置页提供主动查询按钮。不依赖四候选/销售合同就绪，不写批次或执行历史。

- 来源接口：POST `/system/innerOpen/login`，JSON 为 username/password；data.accessToken 或 data.token 用作 Bearer；GET `/system/innerOpen/rate/list` 读取 data 数组的 currency/rate。凭据只取本项目环境变量。
- 来源粒度：每币种的系统当前配置值，无商品/订单粒度。原始 rate 用 Decimal 解析，API 以字符串返回。来源合同版本 `erp-rates-readonly-v1`，与本项目公式版本分开。
- 根据实测各币种数值，推断来源 rate 为“人民币/外币单位”；此方向尚未获得业务确认。参考倒数 `units_per_cny=1/rate` 使用独立50位Decimal上下文，不作价格舍入。该结果仅供查询展示，未接入 Snapshot，不改变核心定价公式。
- `queried_at` 是本地完成采集的UTC时间；`effective_date=null` 表示接口未提供生效日期。上游 now 为响应时间，不能映射为 fx_date。`direction_confirmed=false`、`pricing_ready=false`，不能因查询成功标为当日汇率验收。
- 非标准币种不推断别名；重复币种、缺失/非正/非有限汇率只标记对应行，独立有效币种继续展示。不用默认1修补外币汇率。
