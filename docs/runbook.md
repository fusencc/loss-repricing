# 本地工作台运行手册

主要开发环境为 WSL2。下列 PowerShell 命令适用于 Windows 本地副本。

## 1. 环境与启动

本地运行验证使用Windows、Python 3.13、项目`.venv`及Node/npm。后端Dockerfile目标为Python 3.12；本机没有Docker，容器尚未在本机构建或运行。Compose文件是部署准备，不是生产上线结果。

在PowerShell执行：

```powershell
Set-Location -LiteralPath 'D:\projects\loss-repricing'
.\deploy\start-local.ps1
```

入口：[本地工作台](http://127.0.0.1:18765)。账号`admin`；密码仅在根目录`.env`的`LR_ADMIN_PASSWORD`中查看，不输出、提交或截图。`.env`还保存独立会话密钥，不应上传Git。

启动脚本会在缺少虚拟环境时创建并安装后端依赖，缺少`.env`时生成本地 live 配置，缺少前端构建时安装并构建前端，然后执行数据库迁移，隐藏启动API和worker，等待健康检查。`-NoBrowser`用于不自动打开网页。

若虚拟环境已存在但依赖改动，需要先执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
```

若修改了前端源码，需在`frontend`目录重新执行`npm.cmd run build`；启动脚本不会因已有`dist`而自动重建。

## 2. 停止与重启

```powershell
.\deploy\stop-local.ps1
.\deploy\start-local.ps1
```

脚本依据`runtime/local-processes.json`，同时核对进程路径和命令标记后，使用`taskkill /T /F`结束已确认的本项目进程树。Windows虚拟环境启动器会创建解释器子进程，因此需要连同该子进程停止才能释放监听端口；不会按端口杀掉外部程序。启动、停止及18765端口释放已在本机验证。端口已被其他程序占用时启动会报错，请检查占用者，不要随意结束未知进程。

关闭浏览器不影响worker。停止不会删除数据库、批次或回执。启动失败但已生成进程记录时，先查看日志，再使用停止脚本清理本项目进程。

强制停止后立即重启，旧worker的数据库租约可能还未到期。租约最长120秒，新worker到期后在下一次轮询接管；另需留出取数和计算时间。这段等待不等于任务丢失，不要删锁、清任务或重复点击来催跑。

## 3. 模式与配置

| 配置/模式 | 含义 |
|---|---|
| `LR_ADAPTER_MODE=file` | 读取规范化JSON快照，仅算价对账；不上传、不认定生效 |
| `LR_ADAPTER_MODE=live` | 按确认的数据合同连接真实来源；本轮未配置真实闭环 |
| `LR_LIVE_SUBMIT_ENABLED=false` | 真实提交关闭；运行网页不能越过此环境开关 |
| `LR_SNAPSHOT_PATH` | 文件模式的JSON快照位置 |
| `LR_LIVE_CONTRACT_PATH` | 后续真实合同配置位置；当前示例`verified=false` |
| `LR_DATABASE_URL` | 本项目独立数据库连接，不共享预算业务表或账号 |

首次数据库默认试点店铺为空、自动执行和定时均未启用。file、live 必须使用独立数据库和运行目录；切换环境不复用演示库。核验只处理与当前适配器模式一致的原批次执行，不会用模拟回执终结真实执行；旧模式未结记录仍保留，恢复时应回到其原模式和受控环境处理。


网页上的“暂停”及站点暂停只阻止新提交，仍允许查询已经提交的结果。单条异常“重新评估”只处理所选记录对应的实际上传目标：先核验该目标的未终结执行，再从新快照评估该目标。采集器可能读取完整共享来源，但不会顺带提交其他目标，也不会重传结果未知的旧请求。

## 4. 运行数据与日志

统一技术日志及错误编号的检索方式见[日志与排障](logging-and-troubleshooting.md)。WSL2 使用 `bash deploy/start-wsl.sh`，主开发目录为 `/home/developer/projects/loss-repricing`；Windows 路径是独立旧副本。两端配置、数据库与日志不自动同步。API启动命令已关闭 Uvicorn access log，避免把订单号、查询参数及带权限 URL 写入访问日志。WSL控制台仍接收进程输出；应用技术事件由日志组件另行保存。Windows下列 stdout/stderr 文件仅是进程输出，不是结构化业务证据，也不由应用日志轮转器管理。Windows原生Python当前不具备本实现要求的安全dirfd读取能力，网页日志查询、错误上下文和导出明确返回503；应用安全日志仍可写入，在受控本机查看文件，或使用WSL/Linux网页读取。日志状态中的其他角色文件更新时间只是观察值，不能当作worker存活或业务健康证明。容器Nginx仅记录时间、状态码、耗时及代理自生成编号，原始错误日志关闭；该代理编号不同于应用请求编号。

本地正式记录默认保存在 `runtime/live-history.db`，文件对账默认使用 `runtime/file-reconciliation.db`。显式绑定真实历史库时，live 数据库连接必须与其一致。

常用文件：

- `runtime/api.stdout.log`、`runtime/api.stderr.log`：网页/API进程日志。
- `runtime/worker.stdout.log`、`runtime/worker.stderr.log`：后台任务日志。
- `runtime/local-processes.json`：本项目启动的进程记录。
- `runtime/ui-check`：界面验收截图，不应包含登录密码。

数据库内保存批次快照、判定过程、任务、执行、商品锁、保护配置和审计记录。将来接入真实数据后这些属于业务资料，应限制文件访问；不把原始响应、令牌或带权限下载地址提交Git。

全局概览与异常列表按每个实际目标的最新评估展示，并额外保留尚未结束的旧执行，因此同一目标可能同时有最新判定和旧待核验记录。统计对应这个当前处理集合，不等于去重商品数量。批次详情仍保留全部历史，不会因新评估清掉旧证据。 批次快照记录首次取数，重跑或提交前刷新采用的证据见各商品判定和执行请求。

## 5. 调度、恢复与防重

启用定时后，worker从北京时间09:00起按日唯一键建立任务；11:00是目标时间提示，不是停止处理的硬截止。来源未就绪时，从本次取数失败起等待5分钟后重查，不复用昨日文件。尚未开始的旧日定时任务跨日后取消，新日按自己的定时任务取数。worker正常轮询间隔5秒，待核验记录约每60秒查询一次。通知投递轮询异常单独记录为 `worker.notice_dispatch_failed`，取数、算价和已有调价核验继续按各自状态处理。

上午任务完成后，工作簿保存在 `runtime/morning-logs/YYYY-MM-DD/M.D上午运行日志.xlsx`。名单日记录读取范围、建议价和待处理原因；正式批次记录已保存的实际运行结果，区分建议上传、提交和回读等证据。设置 `LR_DING_TK_MORNING_LOG_FOLDER` 后，用同一部署用户已认证的 `dws` 发布到「集团二部每日数据 → TK亏损提价日志」，已存在的同名文件不会被覆盖。写入失败会保留本地文件及排查编号，对已有工作簿可用 `PYTHONPATH=backend .venv/bin/python -m app.services.morning_log YYYY-MM-DD` 核实后单独补发。

「集团二部每日数据 → 作废订单日志」由 `LR_DING_CANCELLATION_LOG_FOLDER` 单独绑定。只处理上午时段，沿用罗迪的 `M.D上午运行日志.xlsx` 和成功清单、失败清单、汇总三张表。上游将当天真实作废结果放在 `runtime/cancellation-logs/YYYY-MM-DD/M.D上午运行日志.xlsx` 后，上午任务收尾时核对日期和表头并写入钉盘。已有同名文件保留。上游文件未就绪时，查询钉盘当天文件节点或记录待生成状态。手动发布用 `--publish-cancellation`，仅复查用 `--check-cancellation`。

worker和任务使用数据库租约与心跳；持久执行锁按平台、店铺、站点、产品ID、具体商品ID定位实际上传目标。源SKU改名或仓配变化不产生新锁，不能绕过未知执行或72小时保护；算价仍按源SKU严格匹配，不混算不同SKU亏损。顺序为：重新取数和判定 → 保存执行意图及目标锁并提交事务 → 上传 → 保存受理结果 → 查询实际价。

跨北京时间午夜后，昨日尚未上传的拟价停止执行并留在原批次，程序排队采集新业务日数据重算。单目标重评跨日后仍只处理原目标；已有请求不取消、不重传，继续核验。

| 情况 | 程序行为 | 运维处理 |
|---|---|---|
| 来源未就绪 | 任务等待后重查 | 查看四来源日期、完整性和字段错误 |
| 可定位的来源记录异常 | 受影响商品待处理，独立商品继续评估 | 在商品详情查看「来源异常记录」，按来源和记录位置回查 |
| 提交前取数失败 | 本次批次记录失败原因，未发送项等待重取，已发送项继续核验。后台任务按原规则重试 | 查看批次与任务，不按旧拟价手工补传 |
| 提交时超时或进程中断 | 结果未知保留锁，恢复后只查询 | 不删执行记录，不手工重复上传 |
| 查询失败 | 保持待核验和原锁 | 修复连接/合同后继续查询 |
| 行结果确认失败 | 待处理；同目标其他未终结执行仍保留占用 | 修正原因后重新取数评估，不清其他旧请求 |
| 实际价超容限 | 待核验，暂停本站点新提交 | 对账价格口径/活动/舍入；旧提交继续核验，须取得晚于上次超差的新观测才能核验通过 |
| 服务重启 | 从持久任务与执行记录恢复 | 保留数据库与回执，不以重启触发重传 |

“恢复只查询、不重传”针对已有执行意图且结果未知的请求。未发生提交的新任务仍可正常领取；确定失败后的新评估也必须重新通过所有规则。

## 7. 备份与恢复原则

本地备份应保留数据库及必要运行文件。最简单的冷备方式是先用停止脚本停止API和worker，再备份整个`runtime`；需要保留访问方式时，另外安全保管`.env`，不得公开或入Git。运行中的SQLite应使用一致性备份方式，不能只复制主库文件而遗漏WAL中尚未合并的内容。

生产采用独立MySQL一致性备份，同时保存合同版本、应用版本及必要业务文件。恢复前先关闭自动执行和定时，核对快照时间、已有执行意图、商品锁以及外部已生效记录，再恢复查询。不能因数据库回到旧版本就把外部已接受请求重新发送。

代码回滚、数据库恢复与商品价格是三个独立事项。**备份恢复不得自动把商品价格改回旧值，也不得自动生成补偿调价。** 已有价格的处理需依据当前实际价与独立业务决定。

本机演示库已应用稳定上传目标迁移`c41a62f0b931`，迁移前备份保留在`runtime/pre-target-migration.sqlite`。迁移保留原Item键、判定JSON和旧锁，合并目标的未终结执行与最近生效历史；同一目标多笔未知请求须全部终结才释放占用。迁移应在worker停止时执行，遇到无法还原的旧锁会报错停止，不得靠删锁绕过。该安全迁移没有自动降级路径；保留备份不代表可以不核对外部状态就还原后继续自动运行。

## 8. 数据抓取准备好后的接入顺序

1. 提供四份候选、在线商品、汇率、保护/历史及费用配置的脱敏样本，明确日期、单位、数量粒度和稳定明细ID。先与人工导出对账，不猜字段。
2. 在独立 file 环境显式选择已有规范快照的 ERP 算价报告，从网页生成只读文件对账批次，核对最小亏损、换汇、折扣、站点舍入和利润复核。外部整理的当日规范快照通过 LR_SNAPSHOT_PATH 读取。详见 [ERP 文件对账批次](erp-pricing-preview.md)。
3. 根据实际请求/响应建立真实合同与版本，补充分页完整性、来源时间、字段映射、公司模型、税后列、站点精度及 `warehouses` 仓配范围。查价需明确币种映射和 `max_age_seconds` 来源观测有效期，不把测试的 300 秒当作公司已确认参数。异步导出必须绑定提交任务ID，不能挑“最新文件”。
4. 先验证只读取数；保持真实提交关闭。核对当前有效价语义、逐行结果、任务ID与超时后的查询路径。
5. 指定试点店铺/站点，配置独立凭据；在已授权的试点中逐条验证有/无折扣、实际价回读和恢复行为。只有证据完整后才开放相应范围自动执行。

现有公司资产和未确认项见`docs/data-contract-evidence.md`；计算来源见`docs/calculation-and-sources.md`。当前HTTP适配器是合同驱动边界，不是已证明可直接接公司全部接口的成品抓取器。

## 9. 未来生产部署边界

Compose规划为独立`db/api/worker/web`服务，MySQL 8.4；入口预留本机绑定端口18765，后端目标Python 3.12。生产必须有独立数据库/账号、ERP/销售凭据、会话密钥、运行目录、卷和备份，不复制预算项目连接配置。

生产配置校验要求独立MySQL、足够长度的管理员密码与会话密钥、Secure Cookie。还需在入口实际配置TLS和访问控制；设置Secure Cookie本身不等于已经有TLS。当前Compose入口仅绑定回环，外部入口尚需单独部署和验收。

Compose中的真实提交开关保留关闭。生产前需要实际容器构建、迁移、健康、资源、重启恢复与权限核验。本机未安装Docker，以上容器路径尚未完成本地验证；没有完成生产部署。

销售系统使用账号自动登录。`.env` 中填写 `LR_VENDOR_USERNAME` 和 `LR_VENDOR_PASSWORD`，`LR_VENDOR_API_URL` 须与已确认的来源合同地址一致。升级前，原先仅配置 `LR_VENDOR_TOKEN` 的环境应先填写上述配置并移除该变量。只测登录可在根目录 PowerShell 执行：

```powershell
$env:PYTHONPATH='backend'
.venv/Scripts/python -m app.probe_sales_auth --renew-login
```

此命令只调用销售系统登录接口两次，不查询/修改商品，不提交调价文件。Token只缓存内存，后续正常请求前按expires_in自动重新登录。当前未验证refresh_token接口；重复登录可能复用现有Token。命令成功不代表已获调价权限。
