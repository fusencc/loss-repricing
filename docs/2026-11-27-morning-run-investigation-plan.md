## 7. 详细排查顺序提案

用户已要求给出详细排查方式。以下顺序先解决“为什么需要人工接管”，再处理结果同步和耗时，最后逐类补齐业务数据。只在现有归档和隔离环境中做对照；不为了复盘重新拉取几千商品。

### P01：验证正常定时入口能完成整个流程

- **要回答的问题：**去掉本日临时目录中的接续、监看、发通知和补传脚本，正常服务能否独立完成下一轮？
- **证据：**对照 worker → scheduled_departments → erp_workflow → 部门上传 → 通知线程 → 归档的调用；逐一列出 run.py、export22.py、continue_batch.py、supervise.py、classify_remaining_protections.py、send_results.py、finalize_manifest.py、publish_logs.py 替代了哪一步。
- **排查步骤：**先以本日保存的输入和隔离数据库重放编排，用替身记录接口意图；模拟一个部门慢、一个部门已完成，验证已完成部门立即上传；再模拟单条失败和部门异常，检查其他部门与通知、归档能否继续。
- **通过标准：**不需改数据库 Job 状态、不需手工重启或另开按日期写死的脚本；每个部门只进入一次上传，正常完成与部分业务待处理均能自然收尾。真正的定时、认证和生产接口组合，仍要由下一轮自然运行证明，不能用离线重放冒充。
- **拟定修复边界：**先复用现有正式入口解决缺口，不默认再增加一套守护程序、兼容分支或人工操作接口。

### P02：上传任务后来失败时，更新钉钉通知和钉盘日志

这项属于提价后的结果通知与日志模块。上传模块先取得销售系统受理回执，独立任务结果服务随后查询该上传任务是否完成；如果通知已经发出后才确认失败，需要决定原钉盘文件和销售员消息如何更正。这里查询的是上传任务的成败，不读取商品现价，也不改变算价公式。

- **要回答的问题：**用户已收到结果、文件已上传后，明确任务失败如何呈现？
- **证据：**本次 09:27:42 的失败、原发送意图、现 Notice.summary、两份归档与刷新标记机制。
- **排查步骤：**以该条真实事件离线复现 accepted → failed，检查数据库、前端、通知内容和两份文件在每一步的值；用户选定更正方式后，再设计一次性更正及同节点文件更新。
- **通过标准：**提交仍按受理立即记已提价；后续明确失败只改该条和受影响汇总；不阻塞新上传、不回读商品现价、不重复发同一更正、不重提原价格。外部投递结果未知时保留原任务查证。
- **当前选择：**是否补发销售员更正尚未确定，见第 8 节。

### P03：按接口和等待类型解释耗时，继续消除重复取数

- **要回答的问题：**4 小时 13 分钟中，哪些来自外部导出任务等待、哪些是本地串行、哪些是必要逐条请求、哪些确实重复？
- **证据：**两批各约 8 分钟的导出等待，四部控制查询计数，一／五空等 43 分 50 秒和 20 分 51 秒，上传执行时间戳，十二部 59 次真实缓存命中。
- **排查步骤：**从现有证据按“接口＋商品身份＋请求用途＋本轮来源版本”去重计数，分开累加请求耗时与人为等待；核实批量数据已具备的字段，比较新旧输入对相同商品目标价的影响；对尚需 430／385 次的海外仓成本查询，确认是否有已保存或正式支持的批量来源。
- **通过标准：**每个仍存在的逐条请求能说明用途；不重复查询批量导出已经提供的字段；已就绪部门不等其他部门。没有证据前不承诺下一轮能缩短到某个分钟数，也不删除用户要求保留的近期保护。
- **观测缺口：**算价缺少独立起止事件，应只补必要阶段时间和数量，不能引入额外外部自证请求或生产拦截。

### P04：核对通知为何晚发，以及停止主 worker 的连带影响

- **要回答的问题：**价格上传完成后，发送器是否运行、是否满足原有 08:00 起发和个人完成条件、是否因人员目录解析或队列顺序而等待？
- **排查步骤：**按每名销售员记录最后提交时间、通知首次可发时间、实际发送时间和等待原因；区分服务停止、仍有待上传商品、李旺已取消、收件人未唯一匹配等原因；将临时通知器与正式 worker 的入口对照。
- **通过标准：**正常服务能自动发送本轮授权模板；每份未发通知都有可解释原因；一个人未匹配不挡其他人。是否按销售员集中处理上传仅是可讨论优化，不能把用户“像流水线汇总”的要求误解为已经批准改业务顺序。

### P05：验证归档读取量、内容来源和自动刷新

- **排查步骤：**在本地复制的本日数据上检查每个批次快照只读取一次；记录生成时间、行数和资源用量；按当前 groups.rows[].fields 结构核对成功订单归属；验证一个商品关联多订单时的去重计数，再覆盖同节点。
- **通过标准：**完整明细与四部 8,513 条相符；成功清单按订单项计数，有明确商品到订单来源；不会出现未报错但 0 行的假完成；一处发布失败不阻止另一处，也不触发重新采集或提价。迟到失败是否重生成由 P02 的结果同步选择决定。
- **实现边界：**继续采用当前结构，不为旧 files 格式新增兼容双轨；内容核对放在离线验证，避免恢复逐商品生产自证。

### P06：把 441 条缺映射与 4 条任务失败查清楚

- **排查步骤：**先用一／五 59 条已知分类作为目录，扩展到十二／二十二的 382 条；每类给出数量、代表记录、来源字段、拦截位置和能否按现有规则确定。4 条失败分别追到已保存任务响应与失败字段，只有缺失的必要信息才按需补查。
- **通过标准：**每条归入可解释的问题类别，已确定是仓名比较或旧约束误拦的给出最小修正；真正缺少仓成本或商品身份的数据明确缺什么。全程保留用户不处理 VN 误差的边界，不把 576 条超差混入要自动恢复提价的清单。
- **决策边界：**涉及选择哪个有货仓成本等实际业务口径，提供具体记录和选项后再由用户决定；不能借本次汇总直接批量放行。

### P07：统一状态、人员分组和部署证据

- **排查步骤：**对照后台 Item／Execution、接口投影、前端映射、通知摘要、Excel 筛选；用 accepted、明确失败、未知、保护、缺映射各一个案例检查；核对当前源码、实际服务加载文件和前端构建，不覆盖其他未归属改动。
- **通过标准：**同一人在同一视图只出现一个应有分组，商品记录不丢；上传受理显示已提价，明确失败回待处理，未知不被当成可重新提交；文件与消息能标明自己对应哪个结果时点。
- **回归原则：**用少量直接覆盖真实故障的离线检查，完成必要验证即可；不追加与本次问题无关的测试层或生产防护。
